# AGENTS.md

Instructions for AI coding agents (Claude Code or otherwise) working in this repo. Read this before making changes. For full architecture/rationale see [README.md](README.md); this file only covers the rules that are easy to violate by accident.

## Hard invariants — do not break these

1. **`fixtures/script.xml` is read-only.** Never write to it, reformat it, or "fix" it. `fixtureIntegrity.test.ts` hashes it and will fail the build if it changes by even one byte. If you need a modified/new-element XML for a test, build the string in memory (see `xmlParser.newElementSurvival.test.ts`) — never touch the file on disk.
2. **The parser (`src/lib/xmlParser.ts`) has no allowlist.** It must classify nodes only by DOM node type (element/text/comment/CDATA), never by tag or attribute name. Do not add `if (name === "...")` branches there — an unfamiliar element/attribute must survive parsing unmodified with zero parser changes.
3. **Layout vs. field rendering split.**
   - Layout components (`ScriptViewer.tsx`, `Header.tsx`, `PageContent.tsx`) *are* allowed to look for known top-level names (`Client`, `Script`, `Pages`, `Styles`, ...) to decide page structure.
   - Field-level rendering (`FieldGroup.tsx` and anything under it, including `xmlNodeToCleanJson.ts`) must stay driven by node *shape* only (has child elements? just text?), never by name. Don't special-case a field name in there — the whole point is that an unanticipated field renders correctly with no code change.
   - **One documented exception:** `FieldGroup` recognizes exactly 4 reference tag names — `FieldRef`, `NavScreen`, `LabelStyle`, `InputStyle` — to render them as clickable cross-references. All tag-name knowledge for this lives in `src/lib/xmlRefResolver.ts`'s `resolveReference()`; `FieldGroup.tsx` only calls that function and branches on its *result* (resolved vs. not), never on a name directly. If a new field needs special rendering, extend `resolveReference` or add a layout-tier component — don't add another name-literal directly inside `FieldGroup.tsx`.
4. **One parser, every consumer.** `xmlParser.ts` is used unmodified by the test suite, `scripts/generate-json.ts`, and the browser (`useParsedScript.ts`) — including all three of its input sources (the bundled fixture, pasted XML, an uploaded file). Never fork or duplicate parsing logic for one of these call sites.
5. **The UI parses live in the browser** via `useParsedScript.ts` — it does not read the committed `data/script.json`. That file exists only as a reviewable, diffable artifact regenerated by `npm run generate:json`; don't make the frontend depend on it.

## Working conventions

- Run `npm test` before considering any change to `src/lib/` or `src/components/` done — the suite covers round-tripping, ordering, namespaces, comments, CDATA, invalid-XML handling, and cross-reference resolution (`xmlRefResolver.test.ts`).
- `npm run build` (`tsc -b && vite build`) must stay clean; this repo has no `any`-typed escape hatches to lean on.
- New UI components follow the existing pattern: a `.tsx` + co-located `.module.css`, no inline styles, no CSS-in-JS.
- Don't reintroduce a raw `JSON.stringify(node, ...)` dump anywhere — the raw parser AST (`XmlNode`) includes parser-internal fields (`kind`, `namespaceURI`, whitespace-only text nodes). User-facing JSON should go through `elementToCleanJson` (`xmlNodeToCleanJson.ts`), and it should stay scoped to the specific element being viewed, not the whole document.
- CI (`.github/workflows/ci.yml`) runs test + build on every push and PR to `main`. Keep it green; don't add `--no-verify`-style bypasses.
